## 0. 요약

1. **현재 구현은 어테스터당 키 1개, 레지스트리는 정적 설정**입니다. 키 교체·폐기·집합 변경·쿼럼·ERC-1271은 없습니다(§1).
2. **위협의 핵심**: 침해되었거나 거짓말하는 어테스터는 형식상 올바른 허위 증빙을 만들어 냅니다. 서명 검증은 이를 막지 못합니다(README '해결하지 못하는 것'). 이 문서의 완화책은 **피해 범위를 줄이고(쿼럼·폐기) 사후 책임 추적을 가능하게 하는 것**이지 거짓을 거르는 것이 아닙니다(§2).
3. **쿼럼 구조 비교**(§5): (a) 단일 어테스터, (b) 독립된 M개의 v1 어테스테이션이 같은 내용에 합의하는 **합의 계층**, (c) ERC-1271 멀티시그 컨트랙트가 하나의 어테스터 주소 역할, (d) v2 다중 서명 필드(v2는 보류 중). **PoC 기본 제안은 (a)를 유지하고 (b)를 설계로만 확정**하는 것입니다. (b)는 v1 서명 구조·도메인을 바꾸지 않습니다.
4. **어테스터 집합 변경 권한자**(이슈 인수 기준): 새 역할 `ATTESTER_SET_ADMIN`(제안)이 변경을 제안하고, **독립 승인자**(R14의 독립성 기준 재사용)가 승인하는 2자 구조를 기본값으로 제안합니다. 등록은 느리게(2자 승인, 진행 중 IPO 창에는 적용 안 함), 폐기는 빠르게(어테스터 본인 또는 관리자 단독) 하는 **비대칭 권한**입니다(§4.4).
5. **폐기의 효력**: 키가 폐기되면 아직 **확정되지 않은** IPO에 대해서는 그 키의 모든 증빙을 무효로 보는 **소급 무효**를 기본값으로 제안합니다. 침해된 키는 `issuedAt`을 임의로 쓸 수 있기 때문입니다. 이미 확정된 IPO의 기록은 바꾸지 않고 `FINDING_ANNOTATED`류 주석으로만 남깁니다(§4.3).
6. **ERC-1271**: 현재 검증기는 컨트랙트 서명자를 `SIGNATURE_INVALID`로 닫습니다(fail closed). 이 문서는 **PoC 오프체인 엔진에서는 계속 미지원**을 기본값으로 하고, 지원하려면 (i) 서명자 종류를 레지스트리에 **선언**하고, (ii) 가스 한도를 하드코딩하지 않으며, (iii) 상태 의존 결과를 엔진 밖 어댑터가 **블록 기준으로 동결**한 증거로만 엔진에 전달하는 구조를 제안합니다(§6).
7. §9에 테스트 가능한 수용 기준(시나리오 표), §10에 열린 질문 Q13-1~Q13-10(기본값 포함)을 둡니다.

## 2. 위협 모델

### 2.1 신뢰 가정과 범위

| 가정 | 내용 |
| --- | --- |
| TA-K1 | 어테스터는 원장·엔진 운영자와 **다른 주체**다. 단 PoC에서는 시연을 위해 한 사람이 여러 역할을 가질 수 있고, 이때 독립성 주장은 하지 않는다(P14-A03, A-033/A-034 연장) |
| TA-K2 | 어테스터가 자기 데이터원(수탁은행, 펀드회계 등)에서 값을 정직하게 가져온다는 것은 **보증되지 않는다**(README: 쓰레기 입력) |
| TA-K3 | 레지스트리/어테스터 집합 관리자는 이 모델의 신뢰 범위 밖이다. 관리자가 악의적이면 집합 변경이 가능하며, 이 문서는 **탐지 증거와 권한 분리**만 제공한다(#14 T-04와 같은 입장) |
| TA-K4 | 오프체인 PoC는 어떤 체인과도 통신하지 않는다(v1 문서 §3.2). ERC-1271 같은 체인 상태 의존 검증은 이 가정과 충돌한다(§6) |

## 4. 키 수명주기: 등록·회전·폐기

### 4.1 어테스터 레지스트리 모델 (논리 구조, 비규범)

현재의 `attesterId → 주소 1개`를 다음처럼 확장하는 것을 제안합니다. 필드 이름은 제안입니다.

| 필드 | 설명 |
| --- | --- |
| `attesterId` | 논리적 어테스터 ID(조직). 서명 메시지에 이미 들어 있음(v1) |
| `controllerId` | 통제 주체 신고값(독립성 판단용, 자기 신고. P14-A06과 같은 한계) |
| `keys[]` | `{keyId, signerKind: EOA 또는 CONTRACT, address, status, validFromSetSeq, revokedAtSetSeq?}` |
| `status` | `PENDING`(등록 승인 대기) → `ACTIVE` → `REVOKED`. `REVOKED`는 되돌리지 않음 |
| `attesterSetSeq` | 집합이 바뀔 때마다 단조 증가하는 순번. #14의 `registrySeq`와 같은 패턴 |
| `threshold` | 쿼럼 M(§5). 기본 1 |

- **시간이 아니라 순번**을 기준으로 삼습니다. 원장(F1)과 레지스트리(`registrySeq`)가 이미 순번 기준 컷오프를 쓰고, 어테스터의 `issuedAt`(ms)은 서명자 주장이라 키 유효성 판단에 쓸 수 없기 때문입니다.
- 키가 둘 이상일 수 있습니다(회전 중첩, §4.2). 한 키 `address`가 두 `attesterId`에 쓰이는 것은 현재 검증기가 거부하는 중복 주소 규칙을 유지합니다.

### 4.2 등록과 회전

| 절차 | 제안 규칙 | 근거/비고 |
| --- | --- | --- |
| 신규 키 등록 | `ATTESTER_SET_ADMIN`이 제안 → **독립 승인자**가 승인(§4.4) → `attesterSetSeq` 증가, `ACTIVE`. **새 키 소유 증명**으로 새 키가 등록 요청 내용에 서명(도메인 분리된 별도 타입, 이름 제안: `AttesterKeyRegistration`) | 남의 주소를 등록해 사칭하는 것을 막기 위함. v1 증빙 도메인과 섞이지 않게 별도 타입/이름 |
| 회전 | 신규 키 등록(위) → **중첩 기간**에 신·구 키 모두 `ACTIVE` → 구 키 폐기. 중첩 기간의 길이는 정책 값이며 이 문서는 수치를 정하지 않음(근거 없음) | 한 번에 바꾸면 발급 중이던 증빙이 모두 무효화됨 |
| 창 중 제한 | 열린 IPO 창(`attesterSetSeq`가 고정된 구간)에서는 **등록·교체·`threshold` 하향 금지**. 폐기는 허용 | K-A05, 레지스트리 창 중 고정과 같은 패턴(#14 §4.3) |
| 어테스터 본인 요청 | 어테스터가 자기 키를 회전하려면 **구 키 서명 + 신 키 서명** 둘 다를 요청에 붙여 `ATTESTER_SET_ADMIN`이 제출 | 구 키가 이미 침해된 경우에는 이 경로를 쓸 수 없고 관리자 경로로 폐기해야 함 |

### 4.3 폐기와 그 효력

| 항목 | 제안 | 비고 |
| --- | --- | --- |
| 폐기 권한 | **어테스터 본인(해당 키 서명) 또는 `ATTESTER_SET_ADMIN` 단독** 가능 | 폐기는 안전한 방향이므로 빠르게. 오남용 시 가용성 공격(K-A09)이 되나, 등록은 느리게 하므로 균형을 둠. Q13-7 |
| 폐기 이벤트 | 어테스터 집합 로그(append-only)에 `ATTESTER_KEY_REVOKED`(이름 제안)를 기록하고 `attesterSetSeq` 증가 | 원장 `MANAGER_KEY_REVOKED`는 운용사 키용이므로 이 이벤트를 원장에 넣을지 별도 로그로 둘지는 Q13-9 |

| 효력: 폐기 전에 이미 통과된 입찰 | 마감 전이면 해당 입찰을 `EVENT_ANNULLED`(`reason = KEY_COMPROMISE`, #14)로 정정하는 경로를 쓴다. 정정은 #14의 승인자 독립 규칙(R14)을 따름 | #14 §4.4와 같은 순서(① 폐기 ② 새 키 ③ 재기록)를 어테스터 키에도 적용 |
| 효력: 확정된 IPO | **되돌리지 않음.** 확정 이벤트는 불변(D14-Q1). 사후 발견은 `FINDING_ANNOTATED`류 주석으로만 | PoC 한계. 확정 후 침해 발견의 법적·운영적 처리는 범위 밖 |
| 비소급 대안 | 폐기 순번 이전에 소비된 증빙은 유효로 인정 | 침해 키에는 위험. 기본값으로 채택하지 않음(Q13-3) |

### 4.4 어테스터 집합 변경 권한자 (이슈 인수 기준)

| --- | --- | --- | --- | --- |

| 키 등록/회전 | `ATTESTER_SET_ADMIN`(어테스터 본인 서명 첨부) | 독립 승인자 | 느림(창 중 금지) | 〃 |

## 5. 쿼럼 구조 (M-of-N)

### 5.1 선택지 비교

| 안 | 구조 | v1 서명·도메인 영향 | 도메인 모델 영향 | 장점 | 단점 |
| --- | --- | --- | --- | --- | --- |
| (a) 단일 | 현재. `attesterId` 1개, `signature` 1개 | 없음 | 없음 | 단순 | 단일 실패점(K-A01, K-A02) |
| (b) **합의 계층** | 독립된 어테스터 M명이 **각자 v1 증빙을 따로 발급**. 엔진 앞단의 합의 계층이 "내용 일치"를 확인하고 일치하는 서로 다른 어테스터 수 ≥ M이면 하나의 판정 입력으로 합침 | **없음**(각 증빙은 완전한 v1) | `CapacityAttestation` 불변. 새 논리 구조 `AttestationQuorumSet`(제안)과 `contentDigest`(아래) 필요. 저장소는 `(fundId, ipoId)`당 1건이 아니라 `(fundId, ipoId, attesterId)`당 1건으로 변경 필요 | v1 구조·테스트 벡터 유지, 어테스터별 폐기 독립 | 값 일치 정의 필요, 저장소 확장, 프라이버시 확산(K-A11) |
| (c) 컨트랙트 서명자 | 멀티시그/스마트 계정 1개를 어테스터 주소로 등록하고 ERC-1271로 검증 | 스키마 불변(서명 바이트 의미만 달라짐) | `signerKind` 추가 | 쿼럼이 컨트랙트 안에 숨어 엔진은 단일 서명자로 봄 | 체인 의존(§6), 오프체인 엔진과 충돌, 쿼럼 구성을 엔진이 볼 수 없음 |
| (d) v2 다중 서명 | 증빙 하나에 `signatures[]` | 서명 구조 변경 = **v2**. 소유자가 v2를 **보류**함(Q11-1, Q11-4) | `attesterId` → 다중 서명자 | 한 증빙에 모든 서명 | v1 재서명, 호환 파괴, 보류 결정과 충돌 |

### 5.2 PoC 기본 제안

- **기본 (a)** 유지. 즉 현재 동작이 그대로입니다. M=1, N=1.
- **(b)는 설계로 확정하고 구현은 후속**(구현 봇). v2 보류 결정과 충돌하지 않는 유일한 다중 어테스터 경로입니다.
- (c)는 §6의 조건이 충족될 때의 선택지로 남깁니다. (d)는 v2 재개 시 재검토합니다.
- 쿼럼의 효과와 한계를 같이 적습니다: 쿼럼은 **한 키의 침해나 한 조직의 실수**에는 도움이 되지만, **공통 데이터원·공통 소유**에는 도움이 되지 않으며, 금액을 아는 주체를 늘립니다(K-A11).

### 5.3 합의 계층 (b)의 규칙 제안

1. **내용 다이제스트 `contentDigest`**(제안): v1 증빙에서 `attestationId`, `nonce`, `issuedAt`, `expiresAt`, `attesterId`, `signature`를 제외한 필드로 만든 정규 직렬화의 해시. 어떤 필드가 "같은 사실"을 대표하는지는 구현 전에 확정해야 하며(Q13-6), 이 문서는 후보만 제시합니다: `fundId, ipoId, ruleVersion, grossCapacityKrw, underlyingExposures(사전 정렬 후)`.
2. **일치 규칙(기본)**: 위 필드가 **정확히 일치**해야 같은 내용으로 셉니다. 금액 허용오차는 두지 않습니다(허용오차는 규정 근거가 없고 판정 단조성을 해침). 불일치는 `QUORUM_CONTENT_MISMATCH`.
3. **집계**: 서로 다른 `controllerId`의 `ACTIVE` 키 서명이 **서로 다른 어테스터**로부터 M개 이상이어야 `QUORUM_MET`. 같은 `controllerId`는 1명으로 셉니다(K-A03).
4. **집합 고정**: 판정은 IPO 창 개시 시 고정된 `attesterSetSeq`의 구성원·`threshold`만 사용합니다. 창 중 폐기된 키는 그 키의 기여를 뺀 뒤 M 충족 여부를 다시 봅니다(소급 무효, §4.3).
5. **개별 검증 유지**: 각 증빙은 기존 `verifyBid` 단계(만료, 폐기, nonce, 기준일, 서명)를 모두 통과해야 집계에 포함됩니다. 합의 계층은 그 **앞이 아니라 위**에서 동작합니다.
6. **결정성**: 합의 계층의 입력은 (고정된 `attesterSetSeq`의 스냅샷, 증빙 목록)뿐이며 외부 상태를 읽지 않습니다. 같은 입력이면 같은 결과가 나와야 합니다.
7. **결과 표현**: 판정 기록에 사용된 증빙 ID 목록과 `attesterSetSeq`, `threshold`를 남깁니다(재현용). 금액은 기록하지 않습니다(#10 비공개 응답 규율 유지).

### 5.4 도메인 모델 영향 요약 (이슈 인수 기준: "`attesterId` 단일 → 다중 서명")

| 대상 | (a) 유지 | (b) 합의 계층 | (c) 컨트랙트 서명자 | (d) v2 |
| --- | --- | --- | --- | --- |
| `CapacityAttestation.attesterId` | 단일 | **단일 유지**(어테스터마다 별도 증빙) | 단일(컨트랙트 주소의 논리 ID) | 다중 서명자 배열 |

| 저장소 키 | `(fundId, ipoId)` | `(fundId, ipoId, attesterId)` | `(fundId, ipoId)` | `(fundId, ipoId)` |

## 6. ERC-1271 컨트랙트 서명자

### 6.1 표준이 말하는 것 (ERC-1271, 확인일 2026-10-04)

- 서명자가 컨트랙트이면 검증자는 그 컨트랙트의 `isValidSignature(bytes32 hash, bytes signature)`를 호출하고, 성공 시 **매직 값 `0x1626ba7e`** 를 반환해야 합니다. 함수는 상태를 바꾸면 안 되며(`view`) 외부 호출을 허용해야 합니다.
- 구현은 시간 기반·상태 기반 등 **문맥 의존적일 수 있습니다**.
- 보안 고려사항: 가스 한도가 정해져 있지 않아 일부 구현이 많은 가스를 쓸 수 있으므로, **외부 컨트랙트 호출 시 가스량을 하드코딩하지 말라**고 합니다.
- ERC-6492는 **아직 배포되지 않은** 컨트랙트 서명자(counterfactual)를 위한 래퍼 형식을 정의하며, 검증자가 배포를 수행한 뒤 ERC-1271을 호출해야 합니다(`CALL`이므로 재진입 고려). 이 문서는 6492를 **지원하지 않습니다**(배포된 컨트랙트만).

### 6.2 필요한가? (이슈 #13 질문)

| 질문 | 평가 |
| --- | --- |
| 기관 어테스터가 컨트랙트 지갑/멀티시그로 서명할 가능성 | 기관의 실제 서명 인프라는 **확인하지 못함**(P11-A01). 규정은 서명 수단을 정하지 않음 |
| PoC 시연에 필요한가 | 아니오. S1/S2(EOA)로 충분 |
| 쿼럼 달성에 필요한가 | 아니오. (b)로 달성 가능 |
| 온체인 검증(#18/#19)에서 | 선택사항. 온체인 검증기가 있다면 컨트랙트 서명자 지원은 구현 부담이 낮지만, 오프체인 증빙과 서명 의미를 맞춰야 함 |
| **결론(기본값)** | PoC 오프체인 엔진은 **EOA 한정 유지**(현재 fail closed). ERC-1271은 §6.3~6.4의 조건이 합의되면 후속으로 추가. Q13-5 |

### 6.3 지원할 경우의 설계 규칙 (제안)

| 규칙 | 내용 |
| --- | --- |
| 서명자 종류 **선언** | 레지스트리 엔트리의 `signerKind`로 `EOA` 또는 `CONTRACT`를 선언한다. 주소의 코드 유무로 자동 판별하지 않는다(주소의 코드 유무는 시간에 따라 바뀔 수 있고, 판별 자체가 체인 상태 의존이 됨) |
| 해시 | `isValidSignature`에 넘기는 `hash`는 v1의 **EIP-712 다이제스트**(`keccak256("\x19\x01" ‖ domainSeparator ‖ hashStruct(message))`)이다. 스키마·도메인은 v1 그대로 |
| 호출 방식 | 읽기 전용 호출(STATICCALL 또는 `eth_call`). 쓰기 허용 금지 |
| 성공 판정 | 반환값이 정확히 `0x1626ba7e`일 때만 유효. revert, 짧은/긴 반환, 다른 값은 모두 `SIGNATURE_INVALID`(또는 `SIGNER_CONTRACT_CALL_FAILED`)로 **거부** |
| 가스 | **하드코딩하지 않는다**(표준 권고). 대신 검증 환경이 **호출 가스 상한을 설정값으로 갖고** 초과 시 거부한다. 설정값의 수치는 이 문서가 정하지 않는다(근거 없음) |
| 반환 크기 | 반환 데이터 크기에 상한을 둔다(수치는 설정값) |
| 카운터팩추얼(ERC-6492) | 미지원. 배포 전 컨트랙트는 `SIGNER_KIND_UNSUPPORTED` |
| 재진입 | 읽기 전용 호출만 쓰므로 상태 변경 재진입은 없음. 컨트랙트가 임의 코드를 실행하므로 호출 시간 제한(타임아웃)도 설정값 |
| 서명 바이트 형식 | 컨트랙트 서명자의 `signature`는 임의 길이 바이트일 수 있다. v1의 "65바이트·low-`s`" 검사는 `EOA`에만 적용 |

### 6.4 상태 의존성과 결정성 (핵심 문제)

ERC-1271 검증은 **체인 상태에 의존**합니다. 이것은 두 PoC 원칙과 충돌합니다.

1. **결정론적 규칙엔진**: 같은 입력이면 같은 결과가 나와야 합니다(F1, #10). 컨트랙트의 소유자·서명자 집합이 바뀌면 같은 서명이 나중에는 무효가 될 수 있습니다.
2. **오프체인 엔진은 체인과 통신하지 않음**(v1 문서 §3.2).

제안: 엔진이 직접 체인을 읽지 않고, 엔진 **밖의 서명 검증 어댑터**가 ERC-1271 호출을 수행해 다음 **서명 검증 증거**(논리 구조, 이름 제안: `SignatureEvidence`)를 만들어 증빙과 함께 엔진에 전달합니다.

| 필드 | 설명 |
| --- | --- |
| `signerAddress` | 컨트랙트 주소 |
| `digest` | 검증한 EIP-712 다이제스트 |
| `chainId`, `blockNumber`, `blockHash` | 어느 블록 상태에서 판정했는가 |
| `result` | 반환값 또는 실패 사유 |
| `adapterId` | 어댑터 식별자(어댑터 자체가 신뢰 대상임을 드러냄) |

엔진은 이 증거만 소비하고 증거를 **동결**합니다(입력 고정, #10 규칙 버전·입력 고정 원칙과 같은 패턴). 한계: 어댑터와 RPC 제공자를 신뢰해야 합니다. 증거의 위조·선택적 제시를 막는 장치는 이 문서에 없습니다(보안QA 검토 대상). 이 방식이 번거로우면 **지원하지 않는 것(fail closed)이 PoC에는 더 안전합니다.**

## 7. EIP-712 v1 스키마와의 호환

| 항목 | 이 문서의 영향 | 호환 여부 |
| --- | --- | --- |
| 타입 정의 `CapacityAttestation` | 변경 없음 | 호환 |
| 도메인 `{name, version, chainId, verifyingContract}` | 변경 없음. 어테스터 키 등록용 새 타입(`AttesterKeyRegistration`)을 쓸 경우 **별도 도메인 이름**(예: `ipo-proof AttesterRegistry`, 제안)으로 분리해 v1 증빙 도메인과 섞이지 않게 함 | 호환 |
| 서명 필드 | (a)(b)(c)에서는 변경 없음. (d)만 변경(v2 보류) | 호환 |
| 서명 형식 | `EOA`는 v1 규칙 그대로. `CONTRACT`만 별도 규칙(§6.3) | 호환(추가만) |
| `attesterId` 의미 | 논리 ID. 키 회전해도 같은 ID | 호환 |
| 테스트 벡터(§9.2) | 변경 없음 | 호환 |

| 시각 단위 | ms 유지. 온체인 이식 시 변환은 #18 | 해당 없음 |
| 기준일(as-of) 필드 | v2 보류와 무관 | 해당 없음 |
| 공개 금지(§7.0) | 쿼럼 어테스터가 늘어도 서명 메시지·다이제스트·서명은 계속 비공개. 합의 계층 결과 기록에도 금액을 넣지 않음 | 호환 |

| Q13-9 | 어테스터 집합 변경 로그의 위치 | **별도 append-only 로그**(원장과 같은 봉투 형식, 별도 `attesterSetSeq`) | 원장 이벤트에 넣으면 #14 이벤트 목록 변경 필요. 대안: 원장에 `ATTESTER_*` 이벤트 추가 |
| Q13-10 | 키 보관 요구 | S2(KMS/HSM) **권고**, 필수 아님 | 기관 인프라 미확인(P11-A01) |

## 11. 가정, 미확인, 후속

### 11.1 새 가정 (`REGULATORY_ASSUMPTIONS.md` 편입은 리서치 후속 PR에서)

- (새) P13-A01: 어테스터 키 관리·쿼럼은 **규정 요구가 아닌 PoC 설계**다. 규정은 어테스터의 서명 수단·키 관리·쿼럼을 정하지 않는다(확인한 범위에서 찾지 못함).
- (새) P13-A02: 어테스터 조직 간 독립성은 `controllerId` 자기 신고에 의존한다(P14-A06과 같은 한계).
- (새) P13-A03: 기관 어테스터가 EOA 서명(S1/S2) 또는 컨트랙트 서명(S3)을 쓸 수 있는지 **미확인**(P11-A01과 연결).
- (새) P13-A04: 쿼럼의 "내용 일치"는 정확 일치이며 허용오차는 규정 근거 없이 두지 않는다.

### 11.2 미확인

- 기관 어테스터가 사용하는 실제 서명 수단과 KMS/HSM의 secp256k1/keccak-256 지원 여부.
- 임계 서명(S4) 라이브러리 성숙도와 기관 수용.
- 어테스터 집합 로그를 원장 봉투로 둘 때의 이벤트 호환(Q13-9).
- 이 문서는 ERC-6492를 지원하지 않는다고 결정했으나 실제 기관 지갑이 counterfactual 서명을 쓰는지는 확인하지 못함.
